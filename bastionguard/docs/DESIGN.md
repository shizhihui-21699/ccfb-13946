# 设计说明：确认频率的取舍与安全边界

## 1. 要同时满足的四个约束

1. 私钥不能离开运维人员的电脑；
2. 每次借用必须限定到当次真实目标，不该发生的借用要被本人察觉并拒绝；
3. 不能每条命令都弹窗——高频打扰会训练出「无脑点同意」的肌肉记忆，反而更不安全；
4. 多级跳转、批量脚本、长时间挂着的会话都要成立。

经典 `ssh -A` 满足 3、4，但完全放弃 1、2。BastionGuard 用「授权与会话绑定、决策与执行分离」同时满足四者。

## 2. 确认频率：三层策略

| 层级 | 触发条件 | 用户感知 | 安全补偿 |
| --- | --- | --- | --- |
| **auto（静默放行）** | 命中显式窄口径规则：固定用户 + 只读命令前缀 + 可选主机/区域，短 TTL（演示为 10 分钟） | 无弹窗 | 规则必须窄；仍逐条写审计；静默时段自动升级为确认；突发新目标自动升级 |
| **prompt（一次确认/会话）** | 新目标、写操作、无规则匹配 | 每个**会话**最多一次 | 批准产出的 grant 绑定目标与 TTL；会话内后续签名不再问人，但每个签名仍逐次校验 grant |
| **escalate（紧急确认）** | 静默时段内的 auto 请求、突发阈值触发、主机钥变化 | 系统通知带紧急标记、更短超时（90 秒） | 超时即拒，不默认放行 |

另外两条硬规则：

- **显式 deny 规则排在 auto 之前**（首匹配优先），保证最小权限不会被宽松规则覆盖；
- **批量只确认一次**：一次 `batch_open` 列出全部目标与脚本 SHA-256，批准后为每个目标各发一张独立 grant，
  全部绑定同一脚本哈希。脚本改一个字节就是新会话、新审批；即使复用旧会话，哈希不匹配的签名请求也会被拒。

### 为什么「一次确认覆盖整个会话」是可接受的

风险并不随会话内命令数量线性增长——真正的决策点是「**允许这个来源、以这个身份、连这台机器多久**」。
一旦这个决策错误，限制单条命令也挡不住攻击者在一条 `bash` 里做任何事。因此把确认粒度放在会话/目标上，
用 TTL 限定时间窗、用 revoke 与 reaper 提供紧急制动，是噪声与风险的合理平衡点。单条命令级的二次确认只对
高危险命令（可在策略里扩展 `commands` 为精确匹配或引入危险动作分类）保留升级通道。

### 静默时段与突发检测

- 静默时段（默认夜间，演示里设为一分钟窗口便于展示）内，任何本可 auto 的请求都升级为紧急确认——
  人不在电脑前时，「安静」本身就是异常信号；
- 突发检测：滚动窗口内出现超过阈值的**新**目标即升级。跳板机被静默滥用的典型形态，正是短时间内向
  运维人员平时不开的机器发起连接。

## 3. 授权（grant）的数据模型

每张 grant 包含：`会话ID、链ID、跳数、来源节点、用户、目标主机、端口、主机钥指纹、交互/脚本标记、
脚本哈希、过期时间、是否 auto、命中规则名`。

签名请求到达笔记本时依次校验：

1. 消息封缄可打开（ECDH 静态钥钉扎）且 Ed25519 签名有效、发送方是已注册 worker；
2. nonce 未出现过（防重放）；
3. 存在与 `(会话ID, 目标主机)` 匹配且未过期的 grant；
4. grant 的用户、目标与请求一致；批量场景脚本哈希一致；
5. 全部通过才用本机私钥计算 SSH userauth 签名返回——**返回的是签名，不是钥匙**。

批量场景一个逻辑会话对应多个目标，因此授权存储按 `会话 → 主机 → grant` 两级组织；
单个目标完成时只释放自己的 grant，不影响同批其他目标。

## 4. 长会话的生命周期

- grant 一律带 TTL；笔记本侧 reaper 每 5 秒扫描过期授权；
- 过期或 revoke 不只阻止后续签名，还通过 presence 连接向中继下发 `FrameTeardown`，
  中继关闭该逻辑会话下所有连接（批量即全部目标连接）及其到目标的 TCP，数据隧道被真正掐断；
- 笔记本合盖/断网 → presence 断开 → 中继直接拒绝控制面并关闭连接 → worker 收到「agent offline」快速失败，
  而不是悬挂到审批超时。

## 5. 中继为什么是安全的「哑」组件

- 中继持有 mTLS 节点证书，但目标主机的 `authorized_keys` 只认笔记本公钥，节点证书对目标毫无登录效力；
- 控制消息端到端封缄：中继 root 能看到路由元数据（节点、区域、逻辑会话 id），看不到用户、命令、签名内容；
- 回复同样封缄并由笔记本签名，worker 钉扎回复公钥，中继即使做 TLS 中间人也无法注入伪造的「允许」；
- 中继只保留两道**网络层**防线：节点 mTLS 身份与区域目标 ACL（逻辑目标名 → 允许拨号地址的显式映射）。

## 6. 演示中的攻击场景与预期结果

| 场景 | 攻击动作 | 防御结果 |
| --- | --- | --- |
| ① 越权目标 | 用 worker 节点钥向不在 ACL 的 `loot-1`/restricted 区建隧道 | 中继 ACL 直接拒绝，隧道建立不了 |
| ② 合法网段内的敏感借用 | 协议合规地申请到 db-1 执行 `cat /etc/shadow` | 进入笔记本审批队列（命令、链深、来源可见），人工拒绝，审计留痕 |
| ③ 笔记本离线 | 停掉 agent 后发起借用 | presence 消失，中继拒绝控制面，worker 秒级失败 |
| ④ 封缄帧重放 | 抓取真实控制帧原样重发 | nonce 去重丢弃，无任何签名产出 |
| ⑤ 主机钥变化 | 重启目标生成新主机钥（模拟换机/MITM） | TOFU 指纹比对失败，紧急升级人工确认并记 `hostkey_mismatch` |

## 7. 与生产化的差距（演示刻意简化项）

- CA 与节点证书由 `bg-enroll` 本地一次性签发；生产应接入内部 PKI/证书轮换与吊销（OCSP/CRL）；
- 身份包以文件形式拷贝部署；生产应通过带外渠道下发并支持密钥轮换；
- 审批通道是本机 unix socket + CLI；生产可接桌面通知/企业 IM 的审批卡片，决策协议不变；
- 模拟 sshd 只实现 exec/shell 子集；真实目标用标准 OpenSSH，worker 侧 SSH 协议处理无需改动；
- 策略规则用 JSON、前缀匹配命令；生产可引入参数化规则、危险动作分类与策略版本化；
- nonce 缓存与 TOFU 账本在内存/本地文件；多台笔记本场景需集中化（但签名私钥仍保持本机独占）。
